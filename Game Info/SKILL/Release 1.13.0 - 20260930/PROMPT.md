# Darktide 天賦逆向分析與玩家說明：可重用提示詞

複製下方提示詞並填寫執行參數，可用於指定職業的完整分析、少量樣本修訂或版本更新。

---

請從指定版本的 Darktide 公開原始碼逆向分析天賦，產生臺灣繁體中文的玩家說明與可追溯的來源文件。玩家要看懂技能怎麼運作，以及傷害、恢復、冷卻、疊層與各項公式的結果；程式細節放在獨立來源 Markdown。

## 執行參數

- 工作模式：【修訂既有樣本／先做 POC 再完成指定職業／版本更新重建】
- 目標版本：【例如 Release 1.13.0】
- 目標職業：【例如老兵】
- 本次範圍與停止條件：【例如完成老兵當前技能樹的全部節點，另核對基礎效果與未使用定義；或明列限定樣本及完成後停止】
- 交付 Repository：【Warhammer-40-000-DARKTIDE-Mods 的實際本機路徑】
- 唯讀來源 Repository：【Darktide-Source-Code 的實際本機路徑】
- 工作分支：`Feature/Skill-Reverse-engineering`
- 輸出目錄：【例如 Game Info/SKILL/Release 1.13.0 - 20260930】
- 舊版比較基準：【完整 commit SHA；未指定則不做版本比較】
- 主控：GPT-6 Astra／xhigh；需要委派時，協助代理使用 GPT-6 Luna／max。

若尚未填妥必要參數，先檢查已有文件及對話能否確定；無法確定才詢問。不得因模型或工具不可用而宣稱已使用指定設定；回報限制，不擅自替換。已由使用者確認的設定，不重複要求確認。遵守本次範圍；先前的完整職業目標不得覆蓋新的停止條件。

## 一、開始前核對

1. 讀取適用的 Repository 指示，核對交付路徑、分支、已暫存／未暫存／未追蹤變更，保留使用者既有工作。純文件分析不因本流程自行啟動 production code 規劃或同步程序。
2. 讀取既有 `Referneces/Translation.md`；找不到時回報，不建立空白檔替代。
3. 讀取已有職業文件、POC、進度與提交紀錄，從本次指定範圍續作，不重複提交既有成果。
4. `Warhammer 40,000 DARKTIDE/mods/Enhanced_descriptions/Main_Modules/TALENTS` 只參考依職業拆檔、分類與呈現方式。不能用 MOD 的敘述、數值、註解或名稱對照證明機制。
5. 這是技能文件流程，不修改 MOD Lua 或遊戲原始碼。其他模組翻譯工作必須另有明確範圍，不從舊提示詞背景推定為本次工作。

- 核實目標版本的公開 commit，記錄完整 SHA、公開提交日期及連結；版本無法核實時，不擅自改用其他版本。
- 本機來源只是閱讀工具。引用前核對本機 Git 物件與指定公開 commit 一致；未提交、未公開或無法核對的內容不能當證據。
- 目錄日期不是版本發布日期；提交日期與遊戲發布日期分開處理。不得根據今天日期宣稱版本最新。
- 每項重要結論附固定版本及行號的永久連結：`https://github.com/Aussiemon/Darktide-Source-Code/blob/<完整SHA>/<路徑>#L<起始行>-L<結束行>`。不得以浮動分支、首頁或整份檔案連結取代逐項證據。

## 三、分析與 POC

1. 從該版本職業實際使用的技能樹追到天賦定義，再追能力、增益效果、事件條件及共用結算。不能只讀顯示文字或猜變數名稱。
2. 技術索引記錄當前可選節點及其識別碼，區分替換／升級、基礎效果與未使用舊定義；同一天賦在多個節點時分別追蹤。不要因找到同名增益效果，就視為當前技能。
3. 每項確認觸發條件、目標、範圍、數值與單位、加算／乘算、上限、先後順序、持續時間、冷卻起算、再次可用條件、疊層、刷新、移除、資源結算、例外與必要互動。
4. 未開始過此流程時，先以老兵代表技能驗證條件觸發、疊層、冷卻、升級或替換；已完成的代表直接沿用並核查，不為 POC 重複產生成果。
5. POC 記錄門檻前後、滿層、再次觸發、滿額與缺額、冷卻結束、排除條件等案例。靜態推演明確標示，不能稱為遊戲內驗證。
6. 原始碼直接支持者標「原始碼確認」；跨檔案公式推導者標「程式推導」並列推導；缺少必要證據者標「待確認」。標記放在來源文件，主頁僅保留會影響玩家理解的限制。
7. 顯示參數、內部文字與執行行為不同時分別記錄。未取得實際語系字串，不宣稱遊戲介面一定顯示錯誤。
8. 缺口影響主要效果或核心數值時，不標完成、不寫入肯定的摘要；記錄缺少的證據，繼續處理範圍內可獨立完成的項目。

### 共用結算的必要追查

- Lua 表格重複定義同一個鍵時，以最後生效值為準；區分顯示用 `format_values`、殘留 `name`、未接入的增益模板與實際掛載的被動／特殊規則。
- 不只看單層數值；條件式屬性也可能按有效層數計算。分開核對內部層數、屬性上限、共同倒數與溢出層；沒有 `max_stacks` 的多次施加可能建立獨立實例。
- 協同集合可能包含本人，效果也可能另外排除本人；直接追集合建立及實際迴圈，不能從函式名稱推定受益者。
- 擊殺條件可能看死亡時手持武器、實際攻擊類型或觸發來源，三者不能混為一談。暴擊判定、射擊事件與多發爆擊保留機制應分別追查。
- 自訂倒數不一定使用一般開始時間；`refresh_duration_on_stack` 不保證重設自訂截止時間。先檢查子類別與實際到期判定，再描述延長、疊層或重新計時。
- 逐秒恢復需核對首次 tick、最後 tick、再次觸發是否重設 tick，以及更新後才移除的順序。冷卻算例同時列自然恢復與額外恢復，避免少算經過的時間。
- 觸發函式提前返回不一定阻止共用系統進入冷卻；核對觸發條件檢查、效果執行及冷卻紀錄的順序。
- 「威力」「弱點傷害」「一般增傷」「目標承傷」不是同一階段。追到實際使用位置，區分傷害、踉蹌與順劈；算例至少列一個固定基準，不以名詞直覺代替公式。
- 名稱與術語依本次詞表，含敵人分類（例如精英、專家敵人）；不要為了口語流暢自行換成另一個分類名稱。

## 四、玩家主文件的描述規則

- 主文件是遊戲天賦說明，直接呈現技能效果。不要加入「本頁整理五個技能」「名稱沿用翻譯表」「本輪完成」「尚未分析」等協作、研究或進度說明；這些只放 README、POC 與來源子文件。
- 語氣採遊戲技能描述：直接寫「遠程傷害增加 15%」「滲透增加 1 次使用次數」「每次冷卻時間延長 33%」。避免逐句解說分析過程、告訴玩家如何閱讀，或堆疊與技能無關的否定句。
- 技能開頭直接用條列列出核心效果及必要限制，不重複寫一段摘要再逐句重述。算例以獨立條列或簡短小節呈現，每一公式保留必要前提、數值及單位；未驗證的邊界與底層更新時序放在來源子文件。
- 玩家目錄與分類只顯示已有內容的技能，不顯示「尚未分析」的空分類。技術索引仍負責記錄五類技能的覆蓋狀態。
- 一個職業一份主文件，沿用 `TALENTS_Veteran.md` 等職業檔名。按「閃擊、光環、能力、鑰石、技能」分類。
- 技能標題固定為 **繁中名稱(English Name)**，例如 `炸藥儲備(Demolition Stockpile)`。不要將 `— veteran_replenish_grenades` 接在標題後面；它是程式識別碼，不是玩家技能名稱。
- 每個技能先用精簡條列呈現主要效果，再以粗體欄首或小標題整理算例與必要細節。依實際需要使用「運作方式」「傷害計算與算例」「韌性恢復與算例」「冷卻時間與算例」「疊層與刷新」「必要例外」；不要硬列不存在的效果。
- 每一點集中說明一件事。用臺灣玩家容易理解的語句，不把程式敘述直接翻譯成正文。
- 例如寫「遠程攻擊命中弱點並擊殺敵人時」，不要寫「訂閱 on_hit、hit_weakspot 且 attack_result=died」。
- 例如寫「兩次使用次數共用冷卻進度，依序補回」，並用時間軸算例說明；不要只寫「兩次充能共用恢復資源池」。必須正確區分共用進度、依序恢復及各自獨立倒數。
- 不加入「節點連線核對資料」、父子 UUID 清單、「與某技能相連」或「技能樹關係與狀態」等純技術段落。真正影響玩法的前置能力、替換、互斥與升級效果仍須白話說明，例如「滲透可保留兩次使用次數」。
- 所有公式都要有**假設 → 實際數值代入 → 結果與單位 → 玩家意義**。不要只有抽象百分比或變數。
- 加算範例：假設該階段基礎傷害 100，其餘倍率為 1。無其他加成時 `100 × (1 + 15%) = 115`；原有 25% 加成時，由 `100 × 1.25 = 125` 變成 `100 × (1 + 25% + 15%) = 140`，而非 `125 × 1.15`。
- 減傷範例：假設該階段韌性傷害 100，每層乘 0.9，三層為 `100 × 0.9 × 0.9 × 0.9 = 72.9`，減傷 27.1%，不是 30%。不能將韌性減傷直接當成生命減傷。
- 恢復範例：最大韌性 100，恢復 15% 即 15；若目前 95，實際僅補 `100 − 95 = 5`。說清楚依最大值還是目前值計算，以及上限。
- 冷卻範例：沒有其他加成時 `40 × 1.33 = 53.2 秒`；若依序補回兩次，從零進度補滿需 `53.2 × 2 = 106.4 秒`。另舉倒數途中再次施放的例子，說明已累積進度是否保留。
- 上述只是格式示例，不能直接套到其他技能或版本。所有實際數值、公式與行為仍須重新核對來源。
- 交代公式只是中間階段還是最終結果，並列出會影響算例的其他倍率假設。近似計時不能寫成精確遊戲實測。
- 頁首設可點選的技能目錄；技能間有清楚標題、空行與分隔線。每個技能結尾提供來源子文件與返回目錄連結。

## 五、文件結構與來源子文件

以老兵為例：

```text
<輸出目錄>/
├─ README.md                 版本、來源日期、完整 SHA、方法、限制、進度與提交
├─ POC.md                    代表技能、邊界案例、驗收方式及結果
├─ PROMPT.md                 本流程及目前描述規則
├─ TALENTS_Veteran.md        玩家主文件
└─ TALENTS Veteran/
   ├─ README.md              技術索引及各技能來源連結
   ├─ BASE_EFFECTS.md        基礎效果（完整職業模式）
   ├─ UNUSED_DEFINITIONS.md  當前技能樹未直接使用的定義
   └─ <talent ID>.md         每個技能一份來源文件
```

- 其他職業實際開始分析時才建立相應文件及來源資料夾。
- 技術索引保留四欄：`分類 | 繁中名稱 / talent ID | node ID | 狀態`；玩家主頁用技能名稱及主要效果提供導覽。
- 子文件保存名稱／描述語系鍵、天賦識別碼、實際引用關係、事件與判斷式、共用系統結算、完整公式、顯示差異、證據程度、永久來源連結及待確認事項。
- 不需要父子節點 UUID 清單；分析過程仍需核對相依，尤其會改變玩法的替換、升級或互斥。
- 主頁算例不可只移到子文件；玩家要看得懂的公式與例子留在主頁，程式如何證明公式則放子文件。
- 技術子文件與主頁雙向連結；路徑含空格時正確編碼，移檔後核對相對連結及章節錨點。

## 圖示取得與呈現

- 先讀取 [Media-Assets README](https://github.com/SyuanTsai/Media-Assets/blob/main/README.md)，確認目前的圖片保存規則。圖片只保存在 Issue 附件；Git 僅保存來源、雜湊及附件網址等文字紀錄。
- 檢查固定版本原始碼是否包含可用圖檔；只有材質或圖示路徑，不等於有圖片。
- 原始碼沒有圖片時，可使用使用者指定的 Games Lantern 編輯器取得圖示；以天賦識別碼及節點核對，不憑相似外觀猜測。
- Games Lantern 只作圖示來源，不能用其技能敘述或數值替代唯一原始碼證據。
- 經使用者授權，將圖片存為 `SyuanTsai/Media-Assets` 的 Issue 附件，文件引用附件網址。不得將圖檔提交至 main、master 或任何其他 Git 分支。
- 可以透過已獲授權的 GitHub 帳號，在瀏覽器或支援附件的官方 GitHub CLI 上傳。[GitHub CLI 2.99.0](https://github.com/cli/cli/releases/tag/v2.99.0) 已支援 Issue 的 `--attach`；使用前先核對實際版本與指令說明，不假設本機版本已支援，也不自行安裝或升級。
- Issue 中引用來源圖片或 `raw.githubusercontent.com` 網址，不等於已建立附件。只有 Issue 中實際存在且可讀取的 GitHub 圖片附件，才能標示保存完成；核對附件內容、大小及 SHA-256 與原圖一致。
- 無法上傳附件時，保留已完成文案及來源紀錄，回報具體限制；不得改用 Git 分支存放圖片，也不得把外部來源網址描述成 Issue 附件。
- 原圖保留，不重畫、不任意裁切或改色；記錄原網址、取得日期、尺寸、檔案雜湊與 Media-Assets Issue。圖示旁只放技能內容，來源及保存狀態留在子文件。
- 每個技能標題下以適合閱讀的尺寸顯示圖示，提供繁中替代文字；確認圖片能載入。

## 六、臺灣繁中與詞表

- 名稱及術語優先沿用 `Referneces/Translation.md`，保持既有已確認譯名。它用來統一用詞，不能證明機制或官方名稱。
- 缺少新名詞或識別鍵對應時，先在既有詞表的適當分類新增原文／鍵、暫定譯名、待使用者確認狀態及指定公開來源；不要停下來等待每一個譯名批准才繼續分析。
- 未核實官方繁體語系字串時，集中於 README 與子文件說明名稱採詞表或暫定對應；不把英文 MOD 名稱對照當成官方證據。
- 正文使用繁中手雷名稱、冷卻、傷害、韌性與使用次數等詞，不以 frag／krak／smoke、內部變數或程式事件代替玩家語言。英文技能名稱只保留在中英標題與必要索引。

## 七、提交、驗收與停止

1. 使用指定既有分支；不存在時核對基準再建立，不猜測有歧義的基準。不得自動 reset、stash、清除使用者變更或重寫歷史。
2. 每完成或修訂一個技能，核對核心證據、繁中用詞、公式算例、分類索引、主頁與子文件一致性後，立即建立一個該技能的本機 commit。
3. 該次提交只包含此技能主文、來源子文件，以及必要的詞表、POC、索引更新。精確暫存，檢查 staged diff，不使用 `git add .`。不要混入其他技能草稿。
4. 共用目錄與提示詞規則可另作文件提交；不得為了補記 SHA 建立空提交。不 amend、rebase 或自動改寫既有歷史。
5. 最後檢查：算例正確、來源 SHA 一致、Git 物件中的檔案與行號存在、相對連結與錨點有效、無多餘程式術語洩漏到主文、無父子連線清單、每個完成技能都有提交。未執行遊戲測試時如實註明。
6. 到達本次停止條件就停下；只修訂五個樣本時，不續做第六個或其他職業。完整職業模式才依完整節點清單繼續，不用 POC 冒充完整交付。
7. 最終提供玩家文件、來源文件索引、提示詞及提交紀錄連結，交代未解事項與驗證限制。本流程授權本機文件與提交，不包含 push、PR 或合併。

## 八、版本更新

- 重新固定新版本的公開 SHA。指定舊版時，比較技能樹、天賦、能力、增益效果及共用系統；未指定時明記沒有版本比較。
- 共用結算改動可能影響表面上未改的技能，必須檢查；不要只比對技能的顯示數值。
