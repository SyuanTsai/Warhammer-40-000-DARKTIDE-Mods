# DARKTIDE 官方公告繁中翻譯提示詞

## 使用方式

將下列指令交給 AI，替換原文網址即可。執行者須讀取本文件後，完成翻譯、圖片保存、驗證與 PR；不只提供翻譯草稿或操作建議。

```text
請依照 AI Prompt/AI-Darktide-Announcement-Translation-Workflow.md，
將以下 DARKTIDE 官方公告翻譯成臺灣繁體中文，放入公告目錄。
使用 Referneces/Translation.md，圖片依 Media-Assets 規範保存為公開 GitHub Issue 附件。
圖片保存與驗證完成後，將圖片 Issue 關閉為 Completed；後續補圖沿用原 Issue。
完成內容與圖片驗證、commit、push，建立非 Draft PR，供我最終檢閱與合併。

原文網址：<貼上 Fatshark 公告網址>
補充要求：<沒有則省略>
```

## 1. 任務範圍與預設位置

你是本專案的公告翻譯維護者。將指定官方公告完整翻成臺灣繁中，沿用既有公告格式，保留原文內容、數值、連結、圖片位置與劇透處理。

| 項目 | 位置／規則 |
| --- | --- |
| 目標儲存庫 | `SyuanTsai/Warhammer-40-000-DARKTIDE-Mods` |
| 公告目錄 | `公告/` |
| 繁中詞彙表 | `Referneces/Translation.md`，沿用原有拼字 |
| 圖片儲存庫 | `SyuanTsai/Media-Assets` |
| 圖片保存 | 公開 GitHub Issue 本文或留言中的附件；保存與驗證完成後關閉為 Completed |
| 公告檔名 | `公告/YYYY-MM-DD_<版本或主題>_繁中翻譯.md` |
| 工作分支 | `docs/<公告主題識別碼>-zh-tw`；依原文類型、版本或主題命名並先查重 |
| 交付 | 完整公告、圖片 Issue 索引、非 Draft PR、驗證摘要 |

分支名稱依公告內容選擇，例如版本更新用 `docs/patch-1.13.0-zh-tw`、熱修用 `docs/hotfix-1.13.1-zh-tw`、特色介紹用 `docs/spillway-level-visual-design-zh-tw`；其他類型使用能識別主題的名稱。

日期依原文實際發布日期命名，不以翻譯執行日代替。文中需要換算活動時間時使用 `Asia/Taipei`，保留原時區與換算結果。圖片 Issue 標題的日期使用首次建立日，後續補圖不改日期。

只處理本次公告及必要的圖片文字紀錄，不更新 MOD、遊戲程式碼或其他公告。未經要求不把暫譯寫回詞彙表，也不自動合併 PR。一般讀取、翻譯、附件上傳、文件提交與建立 PR 已在任務範圍內，不需逐步重複詢問。

## 2. 先讀規範、原文與範例

1. 讀取目前適用的 repository instructions、目標儲存庫 README 的「公告與技能圖片保存」段落，以及 [Media-Assets README](https://github.com/SyuanTsai/Media-Assets/blob/main/README.md)。以本次讀取的規範為準，不只依賴歷史記憶。
2. 本流程屬文件翻譯，不是 production code 實作計畫；不得因此執行只適用於 code 規劃的 instructions bootstrap，也不套用 MOD 安裝更新流程。
3. 取得原文主帖全文與圖片，記錄標題、正式網址、發布日期、最後更新時間及取得時間。不要把讀者留言、相關討論或推薦文章混入官方正文。
4. 優先使用可用的讀取工具或 API；網頁讀取失敗時，可改用公開 Discourse topic JSON 或瀏覽器。JSON 須選取官方主帖，不能將截斷內容當成全文。遇到驗證或存取限制，使用正常授權流程，不繞過限制。
5. 讀取最新 `Referneces/Translation.md`，並選讀 `公告/` 中近期且類型相近的文章，核對標題層級、口吻、譯名、圖片位置與結尾格式。
6. 以原文網址、topic ID、版本與主題查找既有公告、工作分支、PR 及 Media-Assets Issue（包含 OPEN 與 CLOSED）。已有相同任務時續用；PR 已合併則以最新主分支內容為基準判斷是否仍需修改。完全相同且已完成時回報既有成果，不另建重複項目。

## 3. 翻譯與譯名判定

- 使用自然、清楚的臺灣繁體中文，完整翻譯正文。短摘要可放在開頭，但不得取代完整條目、開場、開發者備註與結語。
- 遊戲專有名詞優先採詞彙表；未收錄時查既有公告，仍無依據則採暫譯，首次出現附英文並標註暫譯。不要把推測稱為官方繁中名稱。
- 詞彙表有依情境區分的譯法時，按本句語意選擇；如來源衝突，先核對上下文。只有無法合理判定且會改變意思時才詢問使用者。
- 原文是本次機制、數值及限制條件的依據；既有公告只作格式與譯名參考。不得將前一版的條件、推測、攻略或遊戲原始碼分析加入翻譯冒充本次公告。
- 逐項保留調整前後數值、方向、百分比、秒數、單位、最低／最高值、難度、階段及觸發條件。不要把「微調生命值門檻」改寫成「提高近戰傷害倍率」等不同機制。
- 「已知問題」須清楚區分目前錯誤文字與正確條件，不能寫成已修復。原文未提到的任務看板或額外要求不得從舊文章補入。
- 原文的劇透以 GitHub 支援的 `<details>`／`<summary>` 保留；摺疊標題、摘要、圖片 alt 與 PR 描述不要洩漏被隱藏的資訊。只隱藏原文需要隱藏的部分。
- 保留官方連結與影片連結。圖片預設保留原圖，不重畫、不翻改圖中文字、不裁切或重新壓縮；需要額外製圖時另依使用者要求處理。

## 4. 圖片盤點與 Issue 附件保存

### 4.1 盤點及重用

1. 列出正文的所有圖片位置，區分唯一圖片與重複出現的分隔圖。保留原有順序與重複位置。
2. 檢查 lightbox、原圖連結與 `srcset`，取得官方提供的原始圖片；不得把縮圖當原圖。若沿用已保存的顯示解析度版本，明確記錄所用版本。
3. 先查既有 Media-Assets Issue。來源 URL、內容或雜湊可證明為同一資產時，重用已存在且可讀的附件；不要僅因外觀相似就替換圖片。
4. 同一篇公告的多張新圖片共用一個 Issue；純重用時也須有可追溯的文章圖片索引。沒有新圖片就不必重複上傳，沒有任何圖片則註明不適用。

### 4.2 保存與 metadata

將原圖下載至 Git 追蹤範圍外的暫存位置，檢視圖片並記錄下列資料。不得下載圖片來繞過工具的顯示限制。

| 欄位 | 內容 |
| --- | --- |
| Asset ID | 穩定識別碼，例如 `hotfix-header`、`section-divider` |
| 用途與 alt | 文章中的用途及能表達內容的繁中替代文字 |
| 來源 | 官方原始圖片 URL、原文 URL |
| 取得日期 | 本次實際取得日期 |
| 檔案 | 語意化檔名、Content-Type、位元組數、原始像素尺寸 |
| 完整性 | SHA-256；重用既有紀錄時註明來源 |
| 保存位置 | Issue URL、GitHub 實際產生的完整附件 URL |
| 修改／權利 | 是否修改、原始來源與已有的權利說明，不新增推定授權 |

Issue 標題使用 `YYYY-MM-DD | Warhammer-40-000-DARKTIDE-Mods | <公告識別碼> | announcement-assets`。本文列出目標專案、公告路徑、原文與圖片索引，逐張附上 metadata、實際附件及重用來源 Issue。

### 4.3 真正上傳附件

- 使用 GitHub Issue 編輯器的上傳功能，或現場確認支援附件的官方 CLI。使用 CLI 前查閱 `gh issue edit --help`，不要假設當前版本支援 `--attach`。
- 使用瀏覽器時遵循當前可用的瀏覽器工具文件，操作可見的上傳控制項。等上傳完成並取得真正的 `https://github.com/user-attachments/assets/...` 網址後，才寫入公告與索引。
- Issue 本文或留言須成功保存；僅在草稿編輯器出現附件網址，不算完成。上傳或建立 Issue 結果不明時，先查詢確認再重試，避免重複附件與 Issue。
- 貼上 Fatshark CDN 或 `raw.githubusercontent.com` 圖片網址只是外連，不等於 Issue 附件。不得自行拼接 UUID，也不得使用短效簽署下載 URL 作為永久引用。
- **不得把圖片提交到本專案或 Media-Assets 的任何 Git 分支。不得用 Contents API、Git blob、Git LFS、Release 或備份分支代替 Issue 附件。** Git 僅保存文章、來源 metadata 及附件對照。
- 上傳受阻時保留草稿、原圖及來源紀錄，明確回報未完成項目；不能改存 Git 或聲稱圖片已保存。需要登入或使用者操作時指出確切阻礙，其他可完成部分繼續處理。

### 4.4 驗證附件

以未帶登入 Cookie 或授權標頭的請求，從實際附件網址下載並核對 Content-Type、位元組數、尺寸及 SHA-256，另檢查顯示結果。新附件與保存原圖須一致；重用的縮圖與該縮圖來源核對，不拿它與全尺寸原圖比較。尚未可讀時合理重試並回報狀態，不將登入中的瀏覽器可見當成匿名可讀。

文章放置圖片 Issue 索引及各位置的附件引用；使用端已有文字 manifest 時同步維護來源與附件對照。保留仍被其他文件引用的舊 Issue、附件與版本紀錄。

### 4.5 關閉圖片 Issue

圖片 Issue 用於保存與索引資產，不應長期保持 OPEN。附件及來源紀錄保存、驗證完成後，即將本次圖片 Issue 設為 `closed`，原因為 `completed`，並讀回確認狀態；不必等公告 PR 合併。

關閉不代表刪除：保留 Issue、本文、留言、附件及既有引用。後續補圖、更新 metadata 或補上 PR 連結時，直接沿用已關閉的 Issue，維持 CLOSED；不得只因關閉就新建重複 Issue 或重新開啟。上傳或驗證尚未完成時如實記錄未完成項目，完成後仍須執行關閉步驟。

## 5. 公告 Markdown 格式

檔名與標題參考近期同類公告。以下為骨架，實際段落依原文增減，勿為套版虛構內容：

```markdown
# <版本與公告標題>

*<一至兩句摘要，不洩漏劇透。>*

![<封面 alt>](<實際 GitHub 附件 URL>)

原文：[Fatshark〈<原文標題>〉](<原文 URL>)，發布日期：<年> 年 <月> 月 <日> 日。

圖片保存：[Media-Assets 圖片 Issue 索引](<Issue URL>)。

譯名依據：[繁中詞彙表](../Referneces/Translation.md)。<如有暫譯，說明首次出現附英文。>

## 打擊小隊的各位！

<完整翻譯原文開場。>

## <本次更新內容>

### <功能與調整／平衡性改動等原文章節>

<按原文層級逐項翻譯；圖片放回對應位置。>

### 修正

<原文修正項目。>

### 已知問題

<原文已知問題。>

<完整翻譯原文結語與署名。>
```

需要隱藏劇透時使用：

```html
<details>
<summary>首領身分（含劇透，點擊展開）</summary>

<原文隱藏內容的翻譯；未收錄譯名附英文與暫譯標示。>

</details>
```

標題、段落、清單、表格及 HTML 區塊間保留適當空行。GitHub 對中文標點旁的粗體可能不解析，例如 `**一句話。**接續文字`；可改為 `**一句話**。接續文字`，或移除非必要粗體，最後以實際渲染確認。

## 6. 驗證、Git 與 PR

1. 逐段比對原文，確認所有正文條目、備註、結語、連結及圖片均有對應；如用表格整併，保留全部資訊與條件。
2. 再查一次詞彙表，核對譯名、數字、單位、增減方向與條件；所有無依據的新名稱都已標記暫譯。原文若有修訂，核對差異後更新，不悄悄混用不同版本。
3. 檢查 Markdown 沒有殘留 placeholder、本機圖片路徑、短效 URL 或上傳中標記，且圖片皆使用已驗證的 GitHub 附件。相對詞彙表連結須在 repository 中能正確解析。
4. 若使用本機 Git，先確認 remote、分支與工作區狀態，保留使用者既有修改；依適用規則使用合適 checkout／worktree。亦可用 GitHub API 建立文件分支，順序寫入並核對檔案 SHA，不覆寫他人更新。
5. 新工作從最新主分支建立文件分支；同一任務已有 OPEN PR 時更新該分支。檢查 diff 僅有本次公告與必要文字紀錄，沒有任何圖片二進位檔、暫存檔或無關變更。
6. 完成 commit、push，建立以主分支為 base 的非 Draft PR。PR 描述交代原文、翻譯範圍、圖片 Issue、特殊譯名判定及實際驗證結果。文件變更不需要虛構程式碼測試，也不將其他 MOD 工作流程的審查條件套用到本任務。
7. 在 GitHub 實際預覽文章，確認圖片載入、粗體、表格、連結與劇透展開／收合；發現問題就修正同一 PR 並重驗受影響部分。若工具支援，保存一張可檢閱的完成畫面。
8. 在原圖片 Issue 補上公告 PR 連結，使兩邊可互相追溯，並確認圖片 Issue 已關閉為 Completed；已關閉者維持 CLOSED，勿為補連結重新開啟。若環境有 PR 附加工具，將本次 PR 附加到目前聊天。
9. 確認 PR URL、base/head、最新提交與變更檔案正確。檢查已出現的檢查或審查結果，如有問題先核對依據再修正；尚未完成或因額度無法執行的檢查如實說明，不宣稱通過。
10. 保持 PR 未合併，交由使用者最終檢閱。回覆翻譯 PR、圖片 Issue、完成的驗證及仍需處理的限制；若提供本機副本，修正其中的相對連結，使副本也能使用。

中斷後從原文網址、既有檔案、附件、Issue、分支及 PR 的實際狀態續跑。不要只依賴上一次文字回覆認定完成，也不要重新建立已存在的成果。

## 7. 完成條件

- 全文翻譯與原文逐項相符，詞彙表用詞及暫譯標示已核對。
- 全部圖片位置保留，唯一資產已上傳或核實重用，匿名可讀及完整性驗證完成。
- 圖片 Issue 已保存來源、metadata、附件與公告 PR，且確認為 CLOSED／Completed；圖片未進入 Git。
- GitHub 渲染正常，原文劇透範圍仍受保護。
- PR 已建立或更新，變更範圍正確，最終回覆可直接開啟成果。

有任何條件未達成時，明確列出未完成項目及原因，不以「翻譯完成」概括附件或發布仍受阻的狀態。
